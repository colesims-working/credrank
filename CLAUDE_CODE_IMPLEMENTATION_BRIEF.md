# CredRank Implementation Brief for Claude Code

Generated by Codex on 2026-04-14 after reading the repo's tracked files plus local-only config surfaces. This is written as an implementation handoff, not a general review.

## Goal

Make CredRank functional for the core user journey:

1. User enters an area, chooses a radius, and searches.
2. The backend finds the broadest practical set of relevant listings inside that radius.
3. Results are filtered more strictly by place type and evidence.
4. Results are ranked with the Bayesian average method.
5. The app fetches as much review signal as the APIs permit and synthesizes useful recommendations.

## Official API Facts To Respect

Verified against Google docs on 2026-04-14:

- Text Search (New) supports `pageSize`, `pageToken`, `includedType`, `strictTypeFiltering`, `locationBias`, and rectangular `locationRestriction`. `maxResultCount` is deprecated. Source: https://developers.google.com/maps/documentation/places/web-service/text-search
- The Text Search REST response can include `nextPageToken`, which is used as `pageToken` for later pages. Source: https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places/searchText
- Place types are split into Table A and Table B. Only Table A values can be used by Text Search's `includedType`; Table B values can appear in responses but cannot generally be used as request filters. Source: https://developers.google.com/maps/documentation/places/web-service/place-types
- Place Details fields `reviews`, `reviewSummary`, and `generativeSummary` trigger Enterprise + Atmosphere billing. Source: https://developers.google.com/maps/documentation/places/web-service/place-details
- `reviewSummary.text` and `generativeSummary.overview` are nested LocalizedText objects, not plain strings. Source: https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places

## Highest Priority Findings

### P0: Search coverage is not actually exhaustive

Problem:

- `search_places()` sends deprecated `maxResultCount` and assumes 60 results per request in `src/credrank/maps_client.py`.
- `grid_search()` stops as soon as `len(all_results) >= max_results` in `src/credrank/grid_search.py`, before ranking. This can skip better places from later subcircles.
- Frontend deep search sends `max_results: 200` in `frontend/index.html`, so "each and every relevant listing" is capped before the user sees coverage state.
- Current subcircle counts are far higher than the comments imply:
  - 1 mi: 1 subcircle
  - 5 mi: 37 subcircles
  - 10 mi: 91 subcircles
  - 20 mi: 271 subcircles
  - 30 mi: 547 subcircles
- `src/credrank/grid_search.py` says a 10-mile radius is about 19 subcircles, but the current algorithm generates 91.

Implement:

- Replace `maxResultCount` with `pageSize: min(20, remaining)` and keep pagination with `pageToken`.
- Track whether each search was saturated: a page limit was hit, a `nextPageToken` remained, or a subcircle produced the API page cap.
- Remove early stopping inside `grid_search()`. Collect all unique candidates for the selected coverage mode, rank after filtering, then truncate only for display if needed.
- Add an adaptive subdivision strategy:
  - Start with larger cells for speed.
  - If a cell saturates, split it into smaller cells until either it no longer saturates or a minimum radius is reached.
  - Return coverage metadata: searched cell count, saturated cell count, failed cell count, deduped count, in-radius count, final count, and `coverage_complete: bool`.
- Make the UI copy honest. Google Places cannot guarantee "every listing"; the app can promise "broad coverage within API limits" and show when results may be incomplete.

Acceptance criteria:

- A deep search never stops before all planned/adaptive cells have been attempted unless an explicit server-side cost/time guard is hit.
- Search responses include coverage metadata.
- The UI displays coverage warnings when a search is capped or saturated.
- Tests assert that later subcircles can contribute the top-ranked result.

### P0: Type filtering is too inclusive for the product need

Problem:

- `src/credrank/relevance.py` explicitly tells the LLM to be inclusive and keep ambiguous matches.
- The taxonomy is stale versus current Google Place Types and mixes filterable and response-only types.
- `filter_by_relevance()` keeps places with no types and accepts any overlap, so a generic `restaurant` type can let unrelated restaurants through for a specific query like "pizza".
- The search request does not use Google-side `includedType` or `strictTypeFiltering`.
- The model does not store `primaryType`, which is critical for stricter filtering.

Implement:

- Add `primary_type: str | None` to `PlaceResult` and include `places.primaryType` in `SEARCH_FIELD_MASK` and details field masks.
- Replace the freeform LLM-only filter with a structured `SearchIntent` object:
  - `query_kind`
  - `included_types` using only Google Table A filterable values
  - `excluded_types`
  - `required_terms`
  - `allow_generic_restaurant`
  - `strictness`
- Use Google-side strict filters where possible:
  - For one specific type, call Text Search with `includedType` and `strictTypeFiltering: true`.
  - For multiple likely types, run one query per included type, merge by place ID, then rank.
- Keep a broad recall pass for food subtypes because Google often labels true matches only as generic `restaurant`; post-filter those candidates by primary type, secondary types, name terms, and optionally details/review context.
- In strict mode, drop no-type places unless there is explicit name/context evidence.
- Add tests for false positives: gas station for pizza, grocery store for tacos, generic restaurant with no pizza evidence, hotel restaurant when searching hotels, etc.

Acceptance criteria:

- "pizza" keeps `pizza_restaurant`, `pizza_delivery`, and generic restaurants with pizza evidence, but drops unrelated generic restaurants.
- "coffee" keeps cafes/coffee shops and drops gas stations or convenience stores unless the query explicitly asks for them.
- Search can gracefully continue if Gemini fails by using deterministic local intent rules.

### P0: Review and recommendation flow is per-place, manual, and loses useful Google summary fields

Problem:

- Search results do not include review text or summaries by design.
- Summaries and recommendations are only fetched after individual button clicks.
- Clicking "Summarize" and "What to order" for the same place calls Place Details twice.
- `reviewSummary.text` is parsed as a dict instead of extracting the nested localized text.
- `generativeSummary.overview` is not parsed at all because the code looks for `generativeSummary.text`.
- Existing `recommend_items()` only generates per-place menu tips; there is no cross-result recommendation synthesis.
- `scripts/what_should_i_eat.py` calls `search_places()` and then `recommend_items()` without Place Details, so it usually has no reviews/summaries to analyze.

Implement:

- Add helper parsers for nested Google LocalizedText fields:
  - `localized_text(value) -> str | None`
  - `review_summary_text(place_json) -> str | None`
  - `generative_summary_text(place_json) -> str | None`
- Add detail caching by `place_id` with a short TTL to avoid duplicate Atmosphere-billed calls during a session.
- Add a batched details/review enrichment step for top-ranked places:
  - Default top N should be configurable, e.g. `REVIEW_ENRICH_TOP_N=10`.
  - Fetch details concurrently with a small concurrency limit.
  - Preserve partial failures per place instead of failing the whole search.
- Add a cross-result recommendation synthesizer:
  - Inputs: ranked top N with ratings, review counts, reviews, review summaries, generative summaries, and editorial summaries.
  - Output: "best overall", "best for X", "what to order", "watch-outs", and short evidence snippets.
  - Return structured JSON and validate it before exposing it to the UI.
- Update the UI to offer one clear post-search action such as "Analyze top results" or automatically analyze top 3-5 with a visible cost/latency state.

Acceptance criteria:

- Place Details parsing tests cover nested `reviewSummary.text.text` and `generativeSummary.overview.text`.
- Repeated summary/recommendation calls for the same place do not fetch details twice within the TTL.
- The app can synthesize recommendations across multiple ranked places, not just one selected place.
- The scripts use `get_place_details()` before calling review-based analysis.

### P1: CredScore currently uses result-set min/max scaling

Problem:

- `rank_places()` sorts by Bayesian average, which is good.
- But CredScore is mapped using the min and max Bayesian average in the current result set when spread is greater than 0.1.
- This means the worst result in a strong set can display as 0, and the best result in a mediocre set can display as 100.
- The README says CredRank uses Bayesian average credibility, but the UI's visible score is relative to each search.

Implement:

- Keep `bayesian_avg` as the canonical ranking value.
- Use a fixed CredScore mapping, preferably `(bayesian_avg - 1.0) / 4.0 * 100`, clamped to 0-100, or document a deliberate alternate mapping.
- Return ranking metadata: `prior_mean`, `confidence`, `rated_count`, and `score_scale`.
- Update tests that currently assert min/max spread to match fixed-score behavior.

Acceptance criteria:

- A 4.6 Bayesian average always displays the same CredScore regardless of the other results.
- UI can still show rank and Bayesian average details.

### P1: Error handling leaks upstream failures as 500s

Problem:

- `search()` does not catch `httpx.TimeoutException`, `httpx.HTTPStatusError`, Gemini errors after `complete()` raises, or grid sub-errors at the top level.
- `grid_search()` catches subcircle failures, but standard search does not.
- `summarize_place()` has no local exception handling around the LLM call.
- `recommend_items()` handles invalid JSON but not LLM transport/model errors.

Implement:

- Convert Maps failures in `/api/search`, `/api/summarize`, and `/api/recommend` to 502/504 with stable JSON details.
- Let relevance filtering degrade to deterministic filtering when Gemini fails.
- Let recommendation synthesis return partial recommendations or a structured "analysis unavailable" field rather than 500.
- Add tests for Maps timeout, Maps 429/500, Gemini failure, malformed LLM JSON, and partial grid failures.

### P2: Replace Basic Auth with a form-based login flow

Problem:

- The current `BasicAuthMiddleware` uses the browser-native Basic Auth dialog.
- 1Password and similar password managers work more reliably with normal HTML username/password fields.
- The desired auth strength is equivalent for this app; the requested change is mainly a better UX layer.

Implement:

- Replace the Basic Auth middleware with cookie/session-based auth.
- Add a `GET /login` route that serves an HTML `<form>` with username and password `<input>` fields.
- Add a `POST /login` route that validates `BASIC_AUTH_USERNAME` / `BASIC_AUTH_PASSWORD` or renamed equivalents.
- Issue a signed, HTTP-only, SameSite cookie after successful login.
- Check the signed cookie on protected routes.
- Redirect unauthenticated browser requests to `/login`.
- Preserve `/health` as unauthenticated for Railway.
- Add `POST /logout` or `GET /logout` to clear the auth cookie.
- Keep local development escape hatch behavior with `ALLOW_UNAUTH=1`.
- Update deployment docs to describe the form login instead of the Basic Auth prompt.

Acceptance criteria:

- 1Password can autofill username/password on `/login` through native form fields.
- Protected routes redirect to `/login` when the session cookie is missing or invalid.
- API requests receive a stable 401/403 JSON response or redirect behavior that the frontend can handle deliberately.
- Session cookies are signed and cannot be forged by editing cookie contents.
- `/health` remains public.
- Existing auth tests are replaced/updated for login success, login failure, logout, cookie tampering, unauthenticated protected route, and `ALLOW_UNAUTH=1`.

## Definition of Done

- User can search any area/radius supported by the UI and receive ranked results with clear coverage metadata.
- Type filtering is stricter and tested, while still preserving true positives with generic Google types.
- Bayesian average remains the ranking method, and CredScore no longer depends on the current result set's min/max.
- Review/detail enrichment is cached, batched, partial-failure tolerant, and exposed through a clear UI action.
- Recommendation synthesis can compare multiple ranked places, not just one selected place.
- The test suite passes and includes the new contracts above.
